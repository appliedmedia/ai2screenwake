# Local stdio MCP

Cancelled calls release both MCP and same-peer IPC notification capacity before replacement through the existing logged `Abandoned` housekeeping event. Lists are bounded and peer-scoped; admitted protection intent is never reversed. This is not a new OwnerControl, MCP tool or public schema. Concurrent-setter tests observe actual owner admission before releasing native work; cancellation fills 32 slots, then proves a replacement setter and recovery query on that same MCP session.

The optional `mcp` feature builds `ai2screenwake-mcp` with the official Rust MCP SDK pinned to `rmcp 3.10.0`, without SDK defaults or HTTP transports. It supports the SDK's known initialization protocol revisions through `2025-11-25`, its latest revision with an `initialize` handshake, and rejects other revisions. The SDK's `2026-07-28` revision replaces initialization with per-request metadata and is not this adapter's lifecycle. This optional target requires Rust 1.88 or later; the default client/native dependency graph and declared workspace baseline are unchanged.

Build from the exact checkout root with `cargo xtask build --profile release`. The canonical builder packages `target/ai2sw/ai2sw.app/Contents/MacOS/ai2screenwake-mcp` beside executable `ai2sw`, displayed as AI2ScreenWake. MCP client configuration names its absolute path as `command` with no arguments. Enclosing-bundle discovery and native LaunchServices resolve the actual `.app` path without an old-basename lookup; stable bundle/IPC identity and the three tools remain unchanged. A direct `cargo build -p ai2screenwake_client --features mcp --bin ai2screenwake-mcp` is useful for focused development, but its unbundled output cannot launch an app. `cargo xtask check` includes the protocol/owner target and canonical bundle; installation and release remain separate, unproved gates.

Initialization advertises the same frozen daily publication version as the app/footer/plist, for example `v2026.11.18(1)`, not Cargo's internal semver. `--build-info` returns version/stamp JSON and exits before runtime/owner admission. Ordinary development builds explicitly identify as `Development`; canonical packaging rejects stale/mismatched producer stamps and initialization versions even at the same source SHA. Discovery still performs no owner or power operation.

Only `is_on`, `turn_on`, and `turn_off` exist, each accepting an empty object. Initialization and tool discovery never resolve an owner or enable protection. A control resolves the binary's actual enclosing `.app/Contents/MacOS`, obtains the native login-session directory, and connects or asks LaunchServices to launch that exact app OFF. There is no environment/path override, shell process, HTTP listener, independent assertion, or automatic TurnOn. An unbundled development executable returns a structured unavailable error, not false Off.

The owner's On result means native-confirmed basic protection with both IOKit assertions and current owner/lifecycle admission. Optional manual-corner denial/unavailability/loss is logged and shown as a visible native-menu limitation, not a fatal MCP error or a claim that corners were protected. Only explicit On may initiate the eligible app's one-shot permission request; discovery/startup/query/Off never prompt. `Filtered` remains original-event deflection, not suppression proof. No public Status/schema/tool changes or signed-app/Dock acceptance follow.

After a genuine basic native failure, queries preserve that operation's first actual fault instead of `protection_unresolved`. Stale failures cannot replace the current cause; explicit Off/retry remains available. The optional modifying mouse-only corner filter requires Accessibility; basic IOKit protection does not.

Native protection also rejects actual CanSystemSleep requests while its basic acquisition is admitted/ready, independently of optional corners. Veto failure remains a structured current-operation fault; WillSleep always allows forced sleep. Native cancellation receipts do not populate the separate paired suppression-proof array or add a tool. This is not a manual-screen-saver veto.

`OwnerAdapter` registers one observation sink, inserts opaque correlation before typed emission, and completes only from `Power::Session::Protection::Settled`. Its bounded notification map drops interest on cancellation, never admitted physical intent. The actual owner transport retains its ten-second connect and five-second operation limits. Protocol framing, outgoing queues, and in-flight IDs are bounded to 64 KiB and 32 requests. A blocked stdout write fails after five seconds. Stdout contains JSON-RPC only; terminal transport diagnostics on stderr omit input payloads.

The durable owner dispatches asynchronously. Native/MCP interleaving scenarios register the native Off request's opaque correlation before emitting, then require its observed successful, confirmed-Off settlement before querying from MCP; emit return and intermediate Pending snapshots are not completion.

After transport and owner-connection cleanup, the binary bounds runtime shutdown to one second: Tokio's macOS blocking stdin read cannot be cancelled and otherwise keeps a failed stdout connection alive indefinitely. Exiting this separate transport process never reverses admitted app-owner intent. A real subprocess regression closes stdout while retaining open stdin and requires a nonzero exit within two seconds.

The backend's optional `mcp-schema` module owns both schema generation and output projection. It serializes actual canonical `Status`, including exact On-only fields, and redacts only internal `failed_genus` from the public three-field error. Text content and `structuredContent` carry the same JSON; `isError` equals error presence. Malformed JSON, invalid JSON-RPC/method parameters, unknown methods/tools, duplicate live IDs, and admission capacity are protocol errors, not successful tool outcomes.

Prepare focused scenarios separately with `cargo test -p ai2screenwake_client --features mcp --test mcp_delivery --no-run`, then run `cargo test -p ai2screenwake_client --features mcp --test mcp_delivery -- --concurrency 3`. The runner resolves feature paths from `CARGO_MANIFEST_DIR` and fails on zero selection. Byte streams isolate protocol behavior. Real-owner scenarios launch two actual stdio subprocesses of the test executable, whose test-only bootstrap injects private Unix sockets and a test-only launcher into the exact production `McpService`; the shipped executable has no such bootstrap. Deterministic native collaborators isolate OS effects without replacing real stdio, IPC, or owner dispatch. A separate scenario runs the actual shipped binary's handshake, discovery, and unavailable-owner result. Each scenario keeps one owner and its client processes rather than restarting them for every assertion; three independent scenarios run concurrently. The master records source-5cc packaged shared-control/error/replay/ordinary-Quit subcriteria. Physical menu/log, real idle/screensaver/security-preservation, supported-runtime and release evidence remain separate unfinished gates, not conclusions from these transport scenarios.

The actual endpoint, 0700/effective-UID ownership and isolation are checked and the chosen policy/location is logged. This runtime-fixture exception never permits authoring source outside the assigned worktree or changing production 94/103/native path, mode or peer guards. Both fitting and simulated-overlong roots have real IPC owner/query/cleanup coverage.
